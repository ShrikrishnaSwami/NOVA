# Windows installation and lifecycle

## Distribution model

NOVA is packaged as a per-user Windows desktop application. It is not installed as a LocalSystem service. A system service cannot safely own the interactive desktop, foreground windows, UI Automation providers, or the signed-in user's notification experience. The desktop process therefore owns the lifetime of a separate, loopback-only FastAPI child process.

## Build locally

Requirements: Windows 10/11 x64, Python 3.12, Git, and Inno Setup 6.

From the repository root:

~~~~powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev,desktop,voice,windows,documents,build]"
pytest -q
.\scripts\build_windows.ps1
& "$env:ProgramFiles(x86)\Inno Setup 6\ISCC.exe" "installer\NOVA.iss"
~~~~

The current packaged release is NOVA 0.1.3 (the next sequential installer release). The portable application folder is created under `dist\NOVA`; its main executable is `dist\NOVA\NOVA.exe`. Keep the entire folder together when moving or running it—the executable depends on the bundled libraries and resources beside it. The installer is `dist\NOVA-Setup-0.1.3.exe`.

The GitHub Actions **Windows installer** workflow runs the test suite and creates two downloadable artifacts:

- `NOVA-Portable-Windows`: a ZIP containing the complete portable `NOVA` folder. Extract it, then run `NOVA\NOVA.exe`.
- `NOVA-Windows-Installer`: the per-user Windows installer, which creates Start Menu shortcuts and manages installation and uninstallation.

To build these artifacts, open the repository's **Actions** tab, select **Windows installer**, and choose **Run workflow**. A `v*` tag also publishes both files to a GitHub Release.

## User data

- Settings: %APPDATA%\NOVA\.env
- Memory database: %LOCALAPPDATA%\NOVA\nova_memory.sqlite3
- Lock file: %APPDATA%\NOVA\nova.lock

The installer copies .env.example into the user settings location only when no settings file already exists. Upgrades do not overwrite user configuration or memory. The application can open the settings file from its tray menu.

## Session lifecycle

- One NOVA desktop process is allowed per user profile.
- The desktop starts hidden when launched with --background.
- The tray icon keeps the UI process alive after the main window is hidden.
- The desktop probes /health before starting the API.
- If it owns the API child, it starts and stops that child. It never terminates an API process it did not create.
- API binding is restricted to loopback for automatic startup.
- The tray's startup toggle changes only the current user's HKCU\Software\Microsoft\Windows\CurrentVersion\Run entry.
- Ctrl+Alt+Space uses the Windows RegisterHotKey API; NOVA does not install a global keyboard hook.

## Notifications

NOVA-generated reply toasts are off by default. The user must enable them from the tray menu; a one-off test notification is also available. Windows notification settings remain authoritative. This installer does not register the restricted userNotificationListener capability and does not read notifications generated by other applications. That requires a separately packaged MSIX identity, capability declaration, OS permission prompt, and additional review/testing.

## Automation contracts

The shared AutomationEngine exposes a finite action registry. It validates a complete plan before any action begins, rejects unknown action types and out-of-range payloads, caps plans at five steps, and stops on cancellation or failure. The desktop remains responsible for showing a clear confirmation before each operation. Typed API endpoints independently enforce their approval flags and parameter constraints.

## Security boundary

NOVA runs as the signed-in user and receives no administrator elevation. It does not install a privileged service, modify Windows system files, disable Defender/UAC, inject into unrelated processes, or execute model-generated shell commands. User data is kept outside the application install directory so updates and uninstall can preserve it.
